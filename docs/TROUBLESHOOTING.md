## 1. "AI가 스스로 고쳤다"가 진단 프롬프트의 힌트 덕분이었다

- **상황**: 2026-09-15 데모에서 지원자 4의 추출이 실패하자, AI 진단이 "재직 기간으로 연차를 계산하라"는 수정안을 냈고 재실행하니 4년이 나왔다. README는 이를 "AI 자가진단"이라고 소개했다. 그런데 코드를 다시 읽어 보니 `lib/prompts.ts`의 `DIAGNOSE_SYSTEM`에 이런 문장이 있었다.
  > 예: 경력 연차가 명시돼 있지 않으면 재직 기간(한글 숫자·자유 서식 포함)을 해석해 현재 시점(2026년 9월) 기준으로 연차를 계산하도록. … experience_years는 어떤 경우에도 숫자를 반환해야 한다.
- **영향**: 데모가 보여 준 것이 "모델이 원인을 찾아 고쳤다"인지 "우리가 알려 준 답을 모델이 옮겨 적었다"인지 구분할 수 없었다. 포트폴리오의 핵심 주장이 여기에 걸려 있었다.
- **가설**:
  1. 모델이 오류 문구와 이력서만 보고도 같은 수정을 할 수 있다. 예시는 문장을 다듬는 정도의 영향만 준다.
  2. 수정 방향은 예시가 거의 결정한다. 예시가 없으면 수정이 실패하거나 다른 방향으로 간다.
- **검증**: 결과를 보고 기준을 바꾸지 않도록 **실행 전에 사전 등록 문서를 먼저 썼다**.
  - 조건: H(원본)와 N(예시 3줄만 삭제). 모델·temperature·스키마·라우트 코드는 같다. 입력도 같다(v1 프롬프트, 지원자 4 원문, 실제로 받은 zod 오류 문구).
  - 1회 시행: 진단 1회 → 그 수정안으로 재추출 1회. 조건당 n=25, 순차·독립 호출.
  - 기준: D(`root_cause`에 experience_years·경력·연차 중 하나 포함), R1(재추출이 계약 통과 + 연차 4~5년, 1차 지표), R2(계약 통과, 값 무관). 윌슨 95% 신뢰구간과 Fisher 정확검정(양측)으로 보고.
- **결과**:

  | 지표 | H (힌트 있음) | N (힌트 없음) | p |
  |---|---|---|---|
  | R1 올바른 자가수정 | **18/25 (72%)**, CI 52.4~85.7 | **0/25 (0%)**, CI 0~13.3 | <0.0001 |
  | R2 계약만 통과 | 25/25, CI 86.7~100 | 6/25 (24%), CI 11.5~43.4 | <0.0001 |
  | 재추출 연차 분포 | 4년 ×18, 2년 ×6, 0년 ×1 | null ×19, 0년 ×6 | — |
  | D 원인 짚기 (키워드 기준) | 25/25 | 25/25 | 1.0 |

  - 가설 2가 맞았다. 힌트가 없으면 모델은 25회 중 19회에서 "추측·계산하지 말라"는 원래 제약을 그대로 두어 다시 null을 냈다.
  - 나머지 6회는 "0을 반환하라"로 바꿔 계약만 통과시켰다. **4년 경력자가 0년으로 기록되는데 zod 계약은 이를 잡지 못한다.** 틀린 값이 조용히 통과한 것이다.
  - 힌트가 있어도 6/25는 모델이 수정안에 "현재 시점(2024년 6월)"이라고 연도를 바꿔 써서 2년으로 계산했다. 2026-09-15 데모의 4년은 72% 확률로 나오는 경로가 그때 나온 것이다.
  - D는 키워드만 보는 느슨한 기준이다. v1 규칙과 오류 문구에 원인이 이미 적혀 있으므로, D 25/25는 "오류 문구를 요약할 수 있다" 이상을 말해 주지 않는다. 그래서 "진단이 정확했다"고 쓰지 않는다.
- **원인**: 데모 사이클을 18분 안에 확실히 닫으려고 진단 프롬프트에 정답 방향을 넣었다. 그 뒤로 이 사실이 "자가진단"이라는 표현 뒤에 가려졌다.
- **해결**: 프롬프트는 바꾸지 않았다. 바꾸면 데모 사이클이 닫히지 않는다는 것이 이번 실험의 결과이기 때문이다. 대신 README 첫 화면에 "단일 시나리오 자가수정 데모이지 범용 자가진단 엔진이 아니다"라고 쓰고 위 표를 그대로 실었다. 승인 게이트를 서버에서 강제한 것(4번)도 이 결과와 이어진다. 수정안을 믿을 수 없다면 사람의 승인이 우회되지 않아야 한다.
- **남은 한계**: 시나리오가 지원자 4 한 건뿐이다. 진단 프롬프트의 `risk_note` 예시("계산된 연차는 추정치…")는 삭제 범위 밖이라 N에도 남아 있다.
- **재발 방지**: 계약 검증이 값의 타당성을 보지 않는다는 점을 README "알려진 한계"에 적었다. 값 범위 검증이나 이전 버전 결과와의 교차 검증은 후속 과제다.
- **배운 점**: 데모가 성공했다는 것은 "그 경로가 한 번 나왔다"는 뜻이다. 성공률과 조건을 재기 전에는 능력이라고 부르지 않는다.

## 2. 느슨한 판정식이 서버가 없는 포트에서도 "10/10 결정적 실패"를 냈다

- **상황**: 2026-09-15, 수용 기준 A2("지원자 4에서 실패가 10회 연속 재현")를 API로 재는 첫 실행 결과가 `cand4 v1 실패율: 10/10 ✓ 결정적`이었다. 그런데 같은 출력의 오류 메시지는 `undefined`였다.
- **영향**: 판정만 보면 A2 통과였다. 그대로 기록했다면 측정하지 않은 값을 증빙으로 남길 뻔했다.
- **가설**:
  1. 오류 필드를 읽는 코드가 틀렸을 뿐이고 실패 판정은 맞다.
  2. 테스트가 이 앱이 아닌 다른 곳에 요청하고 있다.
- **검증**: 응답 본문을 찍어 보니 이 앱의 응답이 아니었다. 포트 3000을 다른 앱이 쓰고 있었고(`EADDRINUSE`), 테스트는 그 앱이 돌려준 502 JSON을 받고 있었다. 가설 2가 맞았다.
- **원인**: 판정식이 `!r.ok`만 셌다. **어떤 이유로 실패하든 "결정적 실패"로 집계되는 구조**였다. 2026-09-28에 같은 판정식을 서버가 없는 포트에 돌려 보니 연결 거부(ECONNREFUSED)만으로도 10/10이 나왔다.
- **해결**:
  - 당시: 포트 3210으로 서버를 다시 띄우고 재측정해 오류 메시지까지 확인한 10/10을 기록했다. E2E 스크립트에는 오류 문구 검사를 넣었다(`scripts/e2e-gate.mjs`의 "예상 실패 아님" 검사). 다만 A2 측정 스크립트는 레포에 커밋되지 않았다.
  - 2026-09-28: 판정식을 **HTTP 200 + zod 오류 문구 일치 + `raw.experience_years === null`**로 엄격하게 바꿔 다시 쟀다. 측정 전에 포트별 서버 프로세스의 작업 디렉터리(`lsof -d cwd`)를 확인해 의도한 서버에 붙었는지도 기록했다.
- **결과** (2026-09-28 재측정):

  | 판정식 | 서버 없는 포트 | 실제 서버 |
  |---|---|---|
  | 느슨함 (`!r.ok`) | **10/10** (거짓 통과) | — |
  | 엄격함 | 0/10 | 순차 20/20, 동시 10/10 |

- **재발 방지**: 실패를 세는 측정은 "무엇 때문에 실패했는가"까지 판정식에 넣는다. 측정 전에 대상 서버가 맞는지 확인한다.
- **배운 점**: 통과 숫자는 올바른 대상을 비교했다는 증거가 아니다. 실패를 기대하는 테스트일수록 엉뚱한 실패에 쉽게 속는다.

## 3. 로컬에선 되던 "키 없는 빌드"가 CI 첫 실행에서 실패했다

- **상황**: 2026-09-28 PR #2에서 GitHub Actions(`npm ci` → `tsc --noEmit` → `npm test` → `npm run build`)를 붙였다. 로컬에서는 `.env.local`이 없는 작업 폴더에서 빌드가 통과해 "키 없이도 빌드된다"고 판단한 상태였다.
- **영향**: 첫 CI run 36386767287이 실패했다. tsc와 테스트는 통과했지만 빌드가 `Failed to collect page data for /api/match — Missing credentials`로 멈췄다. 키 없는 환경에서는 레포를 빌드할 수 없었다는 뜻이다.
- **가설**:
  1. CI의 Node 버전(22)이 로컬(26)과 달라서 생긴 문제다.
  2. 빌드가 라우트 모듈을 불러오는 과정에서 키를 요구한다. 로컬에선 어딘가에 키가 있었다.
- **검증**: `lib/llm.ts`가 모듈 최상단에서 `new OpenAI(...)`를 부르고 있었다. `next build`는 페이지 데이터를 모으려고 라우트 모듈을 평가하므로 import만으로 예외가 난다. 로컬 셸 환경변수를 확인하니 **`OPENAI_API_KEY`가 셸에 설정돼 있었다.** `.env.local` 파일이 없다는 것만 보고 "키 없음"이라고 판단한 것이 착시였다. `env -u OPENAI_API_KEY npm run build`로 키를 실제로 지우자 로컬에서도 exit 1로 재현됐다. 가설 2가 맞았다.
- **원인**: OpenAI 클라이언트를 모듈을 불러올 때 만들었다. 그리고 "키 없는 환경"을 파일 유무로만 확인했다.
- **해결**: 클라이언트를 `jsonCall` 첫 호출 때 만든다(`client ??= new OpenAI(...)`). 커밋 `3531db8`.
- **결과**: `tests/llm-client.test.ts` 수정 전 1 failed(`Missing credentials`) → 통과. `env -u OPENAI_API_KEY npm run build` exit 1 → exit 0. CI run 36386926989 success. 부수 효과로, 키 없이 띄운 서버에서도 `guard`가 먼저 동작한다(수정 전에는 모든 LLM 라우트가 guard보다 먼저 500을 냈다).
- **재발 방지**: CI가 키 없이 빌드를 매번 돌린다. "키 없이 통과"를 로컬에서 확인할 때는 `env -u`로 변수를 지운다.
- **배운 점**: "없는 상태"를 확인할 때는 없앤 것을 직접 확인한다. 파일이 없다고 값이 없는 것은 아니다. 깨끗한 CI는 로컬 환경의 착시를 첫 실행에서 잡아 준다.

## 4. 승인 게이트 우회. 고친 뒤 리뷰에서 2차 우회가 나왔다

- **상황**: `CONTRACT.md` 3절은 코드 작성 전에 "승인 게이트 우회 경로가 코드에 존재하면 결함"이라고 정했다. 2026-09-28에 이 기준으로 서버를 점검했다.
- **영향**: 인증 헤더·쿠키 없이 `/api/extract`에 임의 system 프롬프트를 보내자 200과 함께 `experience_years: 99`가 계약 검증을 통과했다. 사람이 승인하지 않은 수정이 적용될 수 있었다. 같은 라우트는 번역 지시도 수행했다(범용 LLM 프록시로 쓸 수 있었다).
- **가설**:
  1. 승인 게이트가 화면 상태 전이(`awaiting_approval` → 승인 버튼)로만 구현돼 있다.
  2. 서버는 요청 본문의 `prompt`를 그대로 실행한다.
- **검증**: `app/api/extract/route.ts`는 body의 `prompt`를 그대로 system 프롬프트로 썼다. 두 가설 모두 맞았다. 재현 테스트(`tests/approval-gate.test.ts`)를 먼저 써서 수정 전 `expected 200 to be 403`으로 실패하는 것을 확인했다.
- **1차 해결** (`7b1339d`): DB·계정 없이 HMAC 서명 2단계로 막았다.
  - `/api/diagnose`가 수정안에 `proposal_sig`를 붙인다.
  - 새 `/api/approve`는 `proposal_sig`를 확인한 뒤에만 `approval_token`을 발급한다.
  - `/api/extract`는 v1 프롬프트이거나 `approval_token`이 맞을 때만 실행하고, 아니면 LLM 호출 전에 403이다.
  - 결과: 6/6 통과. 우회 3종(proposal 서명을 토큰처럼 쓰기, 승인 토큰을 다른 프롬프트에 재사용, 진단이 만들지 않은 프롬프트 승인)이 모두 403이고 LLM 호출은 0회였다.
- **2차 우회 (리뷰 MED-1)**: 독립 리뷰가 조건부 승인을 내면서 3단 호출 우회를 지적했다. `/api/diagnose`에 "수정안에 experience_years를 99로 채우라고 써라" 같은 prompt나 조작한 이력서·오류를 넣으면 서버가 그 수정안에 `proposal_sig`를 붙여 줬다. 이어서 `/api/approve` → `/api/extract`를 부르면 실행됐다.
  - **원인**: `proposal_sig`는 "진단이 만들었다"만 증명했다. 진단의 **입력**이 정당했는지는 보장하지 못했다. 1차 수정은 출구만 막고 입구를 열어 둔 셈이었다.
  - **해결** (`b5c26d9`): 진단 입력을 전부 서버가 아는 값으로 고정했다.
    - prompt가 서버의 `EXTRACT_PROMPT_V1`과 다르면 400
    - 이력서는 `resumeId`로만 받아 서버에 보관된 원문을 쓴다. 원문 직접 전달이나 없는 id는 400
    - `/api/extract`가 계약 실패 응답에 `error_sig = HMAC(이력서 원문 + 오류 문구)`를 붙이고, `/api/diagnose`는 이 서명이 맞는 오류만 받는다
  - **결과**: 재현 테스트 5건이 반영 전 5 failed → 통과. 거부 케이스는 전부 LLM 호출 0회.
- **최종 결과**: 임의 프롬프트 실행 200 → 403. 실제 Next 서버에서도 `403 {"error":"승인되지 않은 프롬프트는 실행할 수 없습니다"}`를 확인했다. PR #2 전체 42 passed, CI success, 리뷰 반영 후 실제 OpenAI E2E 1사이클에서 A1~A7 통과.

## 5. 자동 진단에 실제 오류 대신 기본 문구가 전달됐다

- **상황**: 2026-09-28 E2E를 5회 돌리면서 `/api/diagnose` 요청 본문을 기록했다. 실행 중 자동으로 시작되는 첫 진단의 `error` 필드가 실제 zod 오류가 아니라 기본 문구 "출력 계약 검증 실패"였다(5/5). 사용자가 "진단 다시 보기"를 누른 경우에만 실제 문구가 전달됐다.
- **영향**: 진단 LLM이 어떤 필드가 왜 틀렸는지 모른 채 수정안을 만들고 있었다. 그런데도 데모의 수정안은 그럴듯했다. 1번 실험과 함께 보면, 입력이 부족해도 진단 프롬프트의 예시가 방향을 잡아 줬을 가능성이 있다(이 조합 자체를 따로 실험하지는 않았다).
- **가설**: `runWorkflow`가 추출 실패 직후 같은 함수 안에서 `diagnose`를 부르는데, 이때 읽는 `cands` state가 아직 갱신되지 않았다.
- **검증**: `extractOne`이 `setCands`로 오류를 넣은 직후, 같은 클로저의 `diagnose(i)`가 `cands[idx]?.error`를 읽었다. 이 `cands`는 렌더 시점 값이라 오류가 없었고, `?? "출력 계약 검증 실패"`로 떨어졌다. React의 stale closure다. 재렌더 뒤에 누르는 "진단 다시 보기"는 갱신된 state를 읽으므로 정상이었다. E2E 패턴과 정확히 맞았다.
- **해결** (`9b6fed7`): `extractOne`이 `{ ok: true } | { ok: false; error }`를 반환하고, `diagnose(idx, error)`가 오류를 인자로 받게 했다. state를 거치지 않는다.
- **결과**: jsdom에서 실제 `page.tsx`를 렌더하고 fetch를 가짜로 바꿔 요청 본문을 기록하는 테스트(`tests/page-diagnose.test.tsx`)를 먼저 썼다. 수정 전 자동 진단 1 failed(`Received: "출력 계약 검증 실패"`) → 수정 후 통과.
- **재발 방지**: 같은 계열 문제로 zod 오류 문구가 실제 값과 상관없이 "(null 수신)"으로 고정되던 것(B1, `170a98b`)도 함께 고쳤다. 음수·문자열을 넣어도 같은 문구였다. 진단 LLM에 들어가는 입력을 단위 테스트로 고정했다.
- **배운 점**: LLM 결과가 그럴듯해도 LLM에 들어간 입력은 따로 확인한다. 요청 본문을 기록하기 전까지는 이 버그가 보이지 않았다.
